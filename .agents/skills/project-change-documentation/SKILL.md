# 同步專案文件

依目前程式碼判斷變更範圍，維護與其直接相關的文件及待辦。

## 工作流程

1. 重新讀取變更檔案與相鄰模組，辨識已改變的行為、公開契約、資料結構與操作流程。
2. 搜尋引用該模組或行為的規格、參考文件與待辦；以程式碼和使用者要求為判斷依據，不以既有文件推測事實。
3. 僅更新確實受影響的文件；若沒有對應文件，判斷是否需要新增與功能相符的文件，而非建立空白或重複文件。
4. 更新 `docs/pending_tasks-list.md`：記錄可追蹤的剩餘工作、風險或後續驗證；已完成且不再需要追蹤的項目應標示為完成或依既有格式移除。
5. 使用可追溯的階段標記，例如 `P2-f`；不要使用對話中的臨時需求編號。必要時僅於彙總處標示一個定案日期；文件內的表格列號可作為表內引用。
6. 在交付內容中列出更新過的文件；若確認無文件需要變動，明確說明判斷依據。

## 判斷界線

- 僅修正程式碼內部實作且沒有公開行為、資料契約或操作方式改變時，通常不需要新規格文件；仍須檢查待辦是否受影響。
- 需求、資料欄位、API 契約或操作流程改變時，必須同步其既有文件，或建立最小必要文件。
- 內容或影響範圍無法依程式碼與使用者需求確定時，先提出具體問題，不臆測文件內容。

## 文件命名

以功能為先、文件類型為後：功能字使用小寫蛇形命名，並以連字號接類型後綴，例如 `user_role_permission-spec.md`。僅使用下列既定後綴；需要新類型時，先擴充此表。

| 後綴 | 用途 |
|---|---|
| `-spec` | 已定案或實作中的功能規格、欄位定義與行為契約。 |
| `-proposal` | 尚待決策的評估、可行性分析與建議。 |
| `-reference` | 工具、流程與對照資料的查詢參考。 |
| `-list` | 待辦、盤點等條列追蹤內容。 |

既有中文命名的開發者指南維持歷史命名，不強制改名。
